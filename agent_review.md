2. Описание правил

Ниже идут правила, по которым нужно выполнять ревью. Нарушения этих правил должны отражаться в ответе.

2.1. Публичный API Flutter-плагина

Публичный контракт пакета желательно сохранять обратно совместимым, если в MR явно не заявлен breaking change.

К ошибкам обычно относятся:

- удаление или несовместимое изменение публичных методов/типов из `lib/flutter_rustore_update.dart`;
- изменение поведения существующего API без обновления документации и миграционных заметок;
- перенос внутренних сущностей в публичный API без необходимости;
- раскрытие сырых платформенных деталей там, где раньше был типизированный Dart API.

Если добавляется новый публичный метод, тип или enum, стоит проверить, что:

- он экспортирован осознанно;
- его поведение описано в README;
- для него добавлены или обновлены тесты.

2.2. Pigeon и синхронизация контрактов

Файл `pigeons/rustore.dart` является источником истины для платформенного контракта.

Если меняется Pigeon-схема, в MR желательно согласованно обновить:

- `pigeons/rustore.dart`,
- сгенерированный Dart-файл в `lib/pigeons/`,
- сгенерированный Android-файл в `android/src/main/kotlin/.../pigeons/`.

Ошибкой считается ситуация, когда изменён только один слой контракта и это создаёт рассинхрон между Dart и Android.

Проксирующие методы без реальной ценности допустимы только если они нужны для сохранения стабильного API. Во всех остальных случаях бессодержательные прослойки — рекомендация к упрощению.

2.3. Архитектура плагина

Проект состоит из нескольких уровней ответственности:

- публичный Dart API в `lib/flutter_rustore_update.dart`,
- типы и расширения в `lib/src/` и `lib/const.dart`,
- Pigeon-контракты в `pigeons/` и `lib/pigeons/`,
- Android-реализация в `android/src/main/kotlin/`.

Нарушениями считаются:

- смешивание registration/plugin lifecycle логики с бизнес-логикой обновлений;
- перенос Android-специфичной логики в публичный Dart API;
- дублирование одной и той же бизнес-логики одновременно в Dart и Kotlin без причины;
- хранение состояния, которое переживает жизненный цикл плагина и может приводить к устаревшим данным или гонкам;
- изменения, которые ломают единственный источник истины для статусов, ошибок и прогресса обновления.

2.4. Работа с потоками, listener и жизненным циклом

`stateStream` и legacy-метод `listener(...)` — важная часть SDK, так как они поставляют состояние обновления во Flutter.

К ошибкам обычно относятся:

- создание утечек подписок, listeners, `EventSink` или Android listener-ов;
- отсутствие `cancel()`/`unregisterListener()`/очистки состояния при остановке стрима;
- потеря событий из-за неправильной логики кэширования последнего состояния;
- замена broadcast-поведения на single-subscription без явной причины;
- изменение semantics legacy API `listener(...)`, из-за которого ломается обратная совместимость.

В рекомендации попадают:

- упрощение работы с подписками;
- улучшение читаемости асинхронной логики;
- оптимизация количества промежуточных объектов.

2.5. Обработка ошибок

Ошибки платформы и RuStore SDK не стоит терять, замалчивать или подменять неинформативным поведением.

К ошибкам обычно относятся:

- проглатывание исключений без проброса в `result.error(...)` или Dart `Future`;
- возврат успешного результата при фактической ошибке;
- потеря кода или смысла ошибки, важной для интегратора;
- изменение логики так, что вызывающая сторона больше не может отличить штатное завершение от ошибки;
- использование логирования как замены корректной обработки ошибки.

Если в MR добавляются новые сценарии ошибок, хорошо отразить их в коде, документации и тестах, когда это применимо.

2.7. Dart null-safety и типизация

Нужно следить за тем, чтобы SDK оставался типобезопасным и предсказуемым.

Ошибками считаются:

- появление небезопасных nullable/non-nullable переходов, способных приводить к runtime-ошибкам;
- невалидные преобразования платформенных значений в enum/typed wrappers;
- возврат слабо типизированных структур вместо уже существующих typed API;
- нарушение инвариантов расширений вроде расчёта `downloadProgress`, статусов и ошибок.

Рекомендациями считаются:

- локальные улучшения читаемости extension-ов и typed mapping;
- замена неоднозначных имён на более понятные.

2.8. Документация и example

Для SDK документация — часть продукта. Если меняется пользовательский сценарий интеграции, README и example желательно поддерживать актуальными.

К ошибкам обычно относятся:

- пример кода, который больше не соответствует реальному API;
- изменение обязательного порядка вызовов без отражения в README;
- расхождение между `README.md`, `README.en.md` и фактическим поведением SDK, из-за которого интегратор с высокой вероятностью реализует сценарий неправильно.

В рекомендации попадают:

- отсутствие описания нового неочевидного сценария;
- неполное пояснение ограничений или edge-case поведения;
- улучшения структуры документации.

2.10. Что считать рекомендацией, а не ошибкой

В Рекомендации, а не в Ошибки, должны попадать:

- улучшения читаемости кода;
- локальный рефакторинг без исправления бага;
- предложение упростить API без текущей поломки;
- замечания по комментариям и формулировкам;
- предложения улучшить структуру README/example, если текущая версия всё ещё корректна;
- замечания по именованию.

Если проблема реально влияет на корректность работы SDK, обратную совместимость, документацию интеграции или жизненный цикл подписок, это уже Ошибка, а не Рекомендация.
